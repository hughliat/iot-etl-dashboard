## 1. 设计概述

### 1.1 需求对齐范围

本设计逐条覆盖 PRD 中 P0（REQ-01 ~ REQ-09）与 P1（REQ-10 ~ REQ-13）全部需求；P2（REQ-14 ~ REQ-16）本期不实现，仅在目录结构与扩展点中预留，不进入编码范围。

### 1.2 设计目标与约束

- **目标**：一条命令在全新环境跑通「采集 → 清洗 → 入库 → 聚合 → 看板」全链路，产出 SQLite 数据库 + 静态 HTML 看板 + 看板 JSON + SQL 优化对比结果；`make test` 全绿。
- **约束**：运行时零第三方依赖（仅标准库）；测试依赖仅 `pytest`；看板无 CDN、无外链；数据确定性可复现；跨平台（Windows / macOS / Linux）。

### 1.3 开放问题决策

PRD 开放问题 O1 / O2 / O3 在本文档关闭，决策如下。

**O1 — 站点数、设备数、采样频率、时长的默认值**

| 规模 | 站点数 | 每站点设备数 | 采样间隔 | 时长 | 预计行数 |
|---|---|---|---|---|---|
| 默认（`make run`） | 5 | 3 | 60 秒 | 30 天 | ≈ 648,000（约 65 万行） |
| 压测（`--scale stress`，供 SQL 优化对比） | 10 | 5 | 30 秒 | 30 天 | ≈ 4,320,000（约 432 万行，百万行级） |

- 行数 = 站点数 × 每站点设备数 ×（86400 / 采样间隔）× 天数。默认规模保证日常演示数秒内跑完；压测规模保证 SQL 优化对比中「全表 SCAN → 索引 SEARCH」在 EXPLAIN 与计时上显著可观测。
- 采样间隔与时长在 CLI 中参数化（`--sites` / `--devices-per-site` / `--interval` / `--days`），默认值如上，任意组合均可复现。

**O2 — Python 版本下限**

- 下限：**Python 3.10**。
- 依据：本项目仅使用标准库（`sqlite3`、`random`、`json`、`argparse`、`datetime`、`pathlib`、`statistics`）与 `pytest`，无 3.11+ 语法依赖；3.10 覆盖 2026 年主流仍在使用的版本（3.10 / 3.11 / 3.12 / 3.13 均可运行），向下兼容面最广。本机实测 3.13 通过。

**O3 — 看板交互（P1）是否引入本地内联 Chart.js**

- 决策：**不引入 Chart.js，用纯 SVG + 原生 JS 实现 REQ-12 交互**。
- 依据：站点筛选与时间范围切换本质是「数据子集过滤 + SVG 折线重绘」，原生 JS 数十行即可完成；不引入第三方前端文件，保持零外链、离线可用，仓库更轻，符合 REQ-05「内嵌 SVG、无 CDN」的刚性约束。
- 备选与取舍：Chart.js 本地内联（约 200KB 第三方源）可提供 tooltip / 缩放等复杂交互，但对本项目「折线趋势 + 多站点对比」属过度设计，列为 P2 扩展，本期不引入。

## 2. 系统架构设计与模块划分

### 2.1 整体数据流

```
generate（确定性随机 + 脏数据注入）
   │  写入
   ▼
ODS：ods_sensor_raw / ods_site / ods_device   ── 原始层
   │  etl.clean（去重 / 异常置空标记 / 单位与字段规范化）
   ▼
DWD：dwd_sensor_clean                          ── 明细清洗层
   │  etl.aggregate（小时 / 天：mean/max/min/std）
   ▼
DWS：dws_sensor_hourly / dws_sensor_daily      ── 汇总指标层
   │  etl.ads（站点 × 小时宽表）
   ▼
ADS：ads_dashboard                             ── 看板输出层
   │  dashboard.export → dashboard.render
   ▼
output/dashboard_data.json + dashboard.html（内嵌 SVG）

optimize.benchmark（并行旁路，读 DWD 明细）
   ▼
output/sql_optimization_report.json（供 README 引用）
```

### 2.2 模块职责

| 模块 | 路径 | 职责 |
|---|---|---|
| 采集模拟 | `src/generate/` | 建表 DDL；确定性随机生成时序数据并注入脏数据；写入 ODS 与元数据表 |
| ETL | `src/etl/` | ODS→DWD 清洗；DWD→DWS 聚合；DWS→ADS 宽表；输出数据质量报告 |
| SQL 优化 | `src/optimize/` | 朴素 SQL vs 索引+重写 SQL，输出 EXPLAIN QUERY PLAN 与多轮计时，结果落盘 |
| 看板 | `src/dashboard/` | ADS→JSON 导出；生成静态 HTML（内嵌 SVG + 原生 JS 交互） |
| 统一入口 | `src/cli.py` | 编排全链路；解析命令行参数；进程退出码 |
| 配置 | `src/config.py` | 集中管理规模参数、种子、传感器定义、路径 |

依赖关系（单向）：`cli` → `generate` → `etl` → `optimize` → `dashboard`；`etl`、`optimize`、`dashboard` 各自依赖 `config`。模块间通过 SQLite 数据库与落盘文件解耦，不互相 import 内部实现（仅 `cli` 调用各模块入口函数）。

### 2.3 关键流程

1. `cli.run_pipeline()` 依次调用：建库 → 采集入库 → 清洗 → 聚合 → 优化对比 → 看板输出。
2. 任一阶段抛出异常，`cli` 捕获并输出错误信息，返回非零退出码；已完成的中间产物保留在 `output/` 供排查。
3. 测试直接 import `generate` / `etl` 的纯函数，不经过 `cli`，避免 IO 耦合。

## 5. 关键技术点与风险

### 5.1 确定性随机与脏数据注入

- 生成仅依赖 `random.Random(seed)`，同参数同种子多次运行逐行一致（REQ-01 验收）。所有随机点（正常值、注入位置、注入类型）均从同一 RNG 流按固定顺序消费，保证确定性。
- 脏数据三类：重复行（复制上一记录）、越界值（生成超范围读数）、缺失值（某字段置 NULL），注入比例固定为小比例（重复 ≈0.5%、越界 ≈0.3%、缺失 ≈0.3%），满足 REQ-01「至少两类可识别脏数据」。

### 5.2 清洗规则（REQ-03）

- 去重：按业务主键 `(site_id, device_id, ts)` 去重，保留首条。
- 异常值：越界值置 NULL 并在 `quality_flag` 标记 `OUTLIER`，不静默丢弃。
- 单位统一：四类读数均为国际单位（℃ / %RH / hPa / μg/m³）。
- 字段规范化：时间戳统一为 UTC `YYYY-MM-DD HH:MM:SS`；字段名统一 snake_case。

### 5.3 SQL 优化对比（REQ-07）

- 场景：「某站点近 7 天 PM2.5 每小时均值」。
- 朴素 SQL：无索引，对 `dwd_sensor_clean` 全表扫描聚合（`EXPLAIN QUERY PLAN` 显示 `SCAN`）。
- 优化 SQL：先建复合索引 `(site_id, ts)`，重写为索引范围扫描 + 分组（`SEARCH`），并利用 `dws_sensor_hourly` 预聚合作为对照。
- 输出：两份 EXPLAIN QUERY PLAN 文本 + 多轮（默认 5 轮）计时均值，落盘 JSON。量化提速比由实际运行得出，不预设进 README。
- 性能目标（压测规模下）：优化后单次查询 < 1 秒；朴素查询秒级，二者差异显著；对比过程总耗时控制在数秒级（符合 PRD 性能非功能要求）。

### 5.4 看板纯 SVG 交互（REQ-05 / REQ-12）

- 折线图用内嵌 SVG `<polyline>`/`<path>` 绘制，无 CDN、无外链。
- 站点筛选、时间范围切换由原生 JS 读取内存中的 `dashboard_data.json` 数据子集，重新生成 SVG 路径；无网络请求、断网可用。

### 5.5 风险与缓解

| 编号 | 风险 | 缓解措施 |
|---|---|---|
| R1 | Windows 环境默认无 `make`，`make run` 不可用 | 提供等效入口 `python -m src.cli run`；Makefile 面向 Linux/macOS 及装有 make 的环境，README 注明两种方式 |
| R2 | 压测规模（432 万行）生成耗时偏长 | 生成流式写入 + 批量事务；默认规模（65 万行）保证日常演示秒级；压测仅 SQL 优化对比触发 |
| R3 | SQLite 数据量过小导致优化对比不显著 | 压测规模达百万行级，EXPLAIN 呈现 SCAN→SEARCH，计时差异显著 |
| R4 | 纯 SVG 交互能力有限 | 本期仅需筛选与时间范围切换，原生 JS 足够；复杂 tooltip/缩放列为 P2 扩展 |
| R5 | 中间产物污染仓库 | `output/`、`data/` 及 `.db`/`.json` 中间产物加入 `.gitignore`，仅保留源码与文档 |

## 7. 环境与命令

### 7.1 依赖

- Python：**≥ 3.10**（仅标准库 + pytest）。
- `requirements.txt`：

```
pytest>=8.0,<9.0
```

- 运行时（`make run`）零第三方依赖，仅用标准库 `sqlite3` / `random` / `json` / `argparse` / `datetime` / `pathlib` / `statistics`。

### 7.2 Makefile 目标

```makefile
PY := python3
PY ?= python    # Windows / 无 python3 时回退

.PHONY: install run run-stress test benchmark clean

install:
	$(PY) -m pip install -r requirements.txt

run:
	$(PY) -m src.cli run --scale default

run-stress:
	$(PY) -m src.cli run --scale stress

test:
	$(PY) -m pytest -q

benchmark:
	$(PY) -m src.cli benchmark --scale stress

clean:
	rm -rf output data
```

### 7.3 等效命令（无 make 环境，如 Windows）

```
python -m pip install -r requirements.txt
python -m src.cli run --scale default     # 等价 make run
python -m src.cli run --scale stress      # 压测规模全链路
python -m src.cli benchmark --scale stress
python -m pytest -q                       # 等价 make test
```

### 7.4 验收自查命令

```
make run       # 产出 output/iot_etl.db + dashboard.html + dashboard_data.json
make test      # 全部用例通过，覆盖去重/异常值/聚合三类核心逻辑
make benchmark # 产出 output/sql_optimization_report.json，EXPLAIN 呈现 SCAN→SEARCH
```
