# 01-总体方案 — IoT 传感器数据 ETL 与可视化项目

## 1. 项目背景与目标

本项目是一个端到端的物联网传感器数据 ETL + 可视化项目，作为个人 GitHub 展示仓库，证明「采集 → 清洗 → 入库 → 指标集市 → 前端看板」的完整链路能力，面向数据开发 / 大模型应用求职方向。

项目与实习经历形成呼应：中电金信阶段的金融投资模块 ETL 采集 / 清洗 / 入湖 / 指标集市经验，直接映射到本项目 ODS → DWD → DWS → ADS 的分层设计；其中「Oracle 索引 + SQL 重写让 BI 查询响应提速 50%」的方法论，在本项目中以 SQLite 的 EXPLAIN QUERY PLAN 与计时对比复现，形成可量化的求职亮点。用友阶段的企业智能体配置交付经验，映射到本项目「自动化编排 + 一键运行」的工程化交付方式。

**成功标准（三条可数验收判据）**：

1. 一条命令 `make run`（或等效入口）在全新环境跑通全链路，产出 SQLite 数据库 + 一个可直接打开的 HTML 看板。
2. README 含架构图、分层说明、快速开始，以及「SQL 重写 + 索引优化」的可量化对比结果。
3. `make test` 全绿，测试覆盖核心 ETL 逻辑。

## 2. 范围边界

**做什么**：

- 模拟多个 IoT 站点与设备，确定性随机生成传感器时序数据（温度、湿度、气压、PM2.5），固定随机种子保证可复现。
- 数据入库到 SQLite，以 schema 命名 + 目录组织体现 ODS → DWD → DWS → ADS 四层数据中台结构。
- 对原始数据做 ETL 清洗：去重、异常值处理、单位统一、字段规范化。
- 按小时 / 天粒度做指标聚合（均值、最大、最小、标准差等）。
- 将看板指标导出为 JSON，生成纯静态 HTML 看板。
- 产出 README（含架构图、分层说明、快速开始、SQL 优化亮点）、核心 ETL 单元测试、一键运行入口。

**不做什么（Out of Scope）**：

- 不接真实硬件，不用真实传感器或真实天气 API。
- 不做云端部署，不做用户登录与权限。
- 不做实时流式处理，本版只做离线批处理。
- 不接企业级数仓引擎（如 Hive、Spark、Doris），分层仅用 SQLite schema 命名体现。
- 不接入本机九域工作台（理由见 5.3 部署形态）。

## 3. 用户与使用场景

**目标用户**：

- 项目所有者本人：作为求职展示，向面试官证明 ETL 与 SQL 优化能力。
- 技术面试官 / 招聘方：通过 README 与可跑通代码快速评估候选人的数据工程基本功。

**核心使用场景**：

- 面试官在全新环境克隆仓库，执行一条命令跑通全链路，看到数据库与看板。
- 面试官阅读 README 中的架构图、分层说明与 SQL 优化对比，理解链路设计。
- 招聘方运行 `make test` 验证核心逻辑的正确性。

## 4. 模块划分

```
src/
├── generate/      # 采集模拟：确定性随机生成传感器时序数据，写入 ODS
├── etl/           # 清洗与聚合：ODS→DWD 清洗、DWD→DWS 聚合、DWS→ADS 宽表
├── optimize/      # SQL 优化对比：朴素查询 vs 索引+重写查询，输出 EXPLAIN 与计时
├── dashboard/     # 看板输出：ADS→JSON 导出，生成静态 HTML
└── cli.py         # 统一入口：编排全链路（对应 make run）
tests/             # 核心 ETL 逻辑单元测试（对应 make test）
output/            # 最终产物：SQLite 数据库 + HTML 看板 + 看板 JSON
```

**各模块职责**：

- **采集模拟（generate）**：按固定种子生成 N 站点 × M 设备的传感器时序数据，含少量人为注入的脏数据（重复行、越界值、缺失值），用于演示清洗必要性。
- **ETL（etl）**：执行四层加工。清洗规则明确、可单测；聚合逻辑抽成纯函数。
- **SQL 优化对比（optimize）**：选一个典型慢查询场景，分别用朴素 SQL 与「加索引 + 重写」的 SQL 执行，输出 `EXPLAIN QUERY PLAN` 结果与多轮计时对比，结果落盘供 README 引用。
- **看板输出（dashboard）**：将 ADS 指标导出为 JSON，生成纯静态 HTML 看板（内嵌 SVG 图表，无外部依赖）。
- **统一入口（cli.py）**：一条命令顺序执行采集 → ETL → 优化对比 → 看板输出。

## 5. 技术路线与选型建议

### 5.1 数据分层（呼应实习数据中台）

| 层 | schema 前缀 | 内容 | 说明 |
|---|---|---|---|
| ODS 原始层 | `ods_sensor_raw` | 模拟采集的原始时序数据，保留原始单位与采集状态，含脏数据 | 对应「采集入湖」 |
| DWD 明细清洗层 | `dwd_sensor_clean` | 清洗后的明细：去重、异常值置空或标记、单位统一、字段规范化 | 对应「清洗」 |
| DWS 汇总指标层 | `dws_sensor_hourly`、`dws_sensor_daily` | 按小时 / 天的均值、最大、最小、标准差等聚合指标 | 对应「指标集市」 |
| ADS 看板输出层 | `ads_dashboard` | 看板直接消费的指标宽表，导出 JSON | 对应「看板输出」 |

分层只用 SQLite 的 schema 命名 + 目录组织体现，不上真实数仓引擎。

### 5.2 技术选型

| 项 | 选择 | 依据 | 备选 | 取舍 |
|---|---|---|---|---|
| 语言 | Python 3（标准库优先） | 纯 Python 生态、可复现、数据开发方向通用 | — | 已锁定 |
| 数据库 | SQLite（标准库 `sqlite3`） | 零外部服务、文件级可复现、原生支持 `EXPLAIN QUERY PLAN` | DuckDB（分析更强但增依赖）；PostgreSQL（需外部服务，破坏可复现） | 选 SQLite |
| 数据生成 | `random` + 固定 seed | 确定性可复现，零第三方依赖 | Faker（更真实但非确定性、增依赖） | 选 random + seed |
| 看板 | 纯静态 HTML + 内嵌 SVG 图表 | 无 CDN、离线可用、呼应「CDN 离线不可用」风险 | Chart.js（本地内联或 CDN） | 优先纯 SVG；交互复杂时本地内联 Chart.js |
| 测试 | pytest | 行业标准、断言清晰 | 标准库 unittest（零依赖） | 选 pytest，依赖极小 |
| 依赖管理 | `requirements.txt` + `Makefile` | 最小依赖、跨平台可复现 | `pyproject.toml` + `poetry` | 选轻量方案 |

**数据规模设计（使 SQL 优化可观测）**：默认 5 站点 × 3 设备、每分钟 1 条、30 天，约 65 万行；另提供压测规模（百万行级）用于 SQL 优化对比，确保索引收益可被 EXPLAIN 与计时显著呈现。具体采样频率、时长、设备数由开发设计阶段确定。

### 5.3 部署形态（不接工作台）

本项目**不接入本机九域工作台**，作为独立项目交付到 GitHub。理由：

1. 目标是「可直接 push 到 GitHub」的展示仓库，独立目录结构最契合。
2. 看板需在全新环境一键跑通，接入本机 8765 服务会引入本机路径与常驻服务依赖，破坏可复现性。
3. 输出物是文件级产物（SQLite + HTML），天然独立、可随仓库分发。

若后续想在个人工作台展示，可把 `output/` 下的 HTML 看板产物登记到工作台应用模块，属可选扩展，非本期目标。

### 5.4 数据存哪

- 模拟数据直接写入 SQLite 数据库（`output/iot_etl.db`），不落地中间 CSV；可选导出 CSV 快照到 `data/` 供人工查看，`data/` 与中间产物一并 gitignore。
- 看板数据由 ADS 层导出为 JSON（`output/dashboard_data.json`），前端 HTML 读取渲染。
- 所有数据为确定性生成，无真实数据、无密钥、无账号。

## 7. 风险识别与应对

| 编号 | 风险 | 等级 | 发生概率 | 缓解措施 |
|---|---|---|---|---|
| R1 | 传感器数据来源依赖外部 API 不可控 | 中 | 高（若依赖外部） | 用确定性随机模拟生成，保证可复现，不依赖外部 API |
| R2 | 前端图表依赖 CDN 离线不可用 | 低 | 中 | 优先纯 SVG / 内联 JS，避免 CDN |
| R3 | 项目定位模糊（数据开发 vs 大模型方向） | 低 | 中 | 突出 ETL + SQL 优化亮点，弱化无关内容 |
| R4 | SQLite 数据量过小导致优化对比不显著 | 中 | 中 | 设计压测规模（百万行级）使索引收益可观测 |
| R5 | 看板纯 SVG 交互能力有限 | 低 | 低 | 静态 SVG 满足趋势展示；需 tooltip 等交互时本地内联 Chart.js |

以上风险 R1–R3 沿用总控计划登记口径，R4–R5 为方案阶段新增。
